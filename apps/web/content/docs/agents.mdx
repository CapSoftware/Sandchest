Anything you can do in the dashboard, your agent can do for you: set Sandchest up, pay for it, start deep scans, read findings, fix them and change settings. You only step in where a person has to: approving the agent once, installing the GitHub App, and the first card payment, which Stripe takes from you directly.

## The quickest way

Press **Set up with your agent** on the home page (or **Let your agent do it** while setting up), and paste the prompt into your agent. It reads this page and does the rest. The prompt is:

```text
Set up Sandchest for me: it finds exploitable vulnerabilities in my GitHub repositories (https://www.sandchest.com).
Read https://www.sandchest.com/docs/agents.md and follow it. Connect to its MCP server (https://www.sandchest.com/api/mcp) if you can add one, otherwise use its HTTP API with the device flow.
Then call get_me and work through next_steps. Only ask me for what needs me: approving the connection, installing the GitHub App, and paying on Stripe if there are no free credits.
```

## For agents: how to set Sandchest up

If you are an agent asked to set Sandchest up, do this:

1. **Connect.** Add the MCP server if your harness supports remote MCP servers ([below](#connect-over-mcp)); it signs in with OAuth and the person approves it in their browser. Otherwise use the [device flow](#connect-over-http) over HTTP and keep the API key it returns (store it as `SANDCHEST_API_KEY`).
2. **Call `get_me`** (`GET /api/v1/me`). It returns who you act as, their GitHub accounts, and `next_steps`: what is left to do, in order. Work through them.
3. **No accounts?** The person must install the GitHub App on their account and choose repositories: give them `links.install_github_app`. Then call `list_accounts` with `wait=50`: it returns as soon as the account shows (call it again if they're not done).
4. **No plan?** If `free_credits` is open for the account, call `claim_free_credits`: no card needed. Otherwise call `quote_credits`, tell the person the price, and call `buy_credits`. The first purchase returns `checkout_url`: give it to the person to pay on Stripe, then call `get_billing` with `wait=50`, which returns once the plan is active. After that, `buy_credits` charges the saved card straight away.
5. **Scan.** Recon maps every repository on its own once there is a plan. Call `start_deep_scan` for a repository (the account's first deep scan is free), then `get_scan` with `wait=50` until `done` is true.
6. **Fix.** In a checkout of a repository, `get_findings_prompt` with `repo` set gives one prompt that covers its open findings (or `get_fix_prompt` for one at a time). Fix them there. When the fix reaches the default branch, Sandchest checks it and marks the finding fixed.

Accounts can be named by GitHub login (`acme`) and repositories by full name (`acme/api`) everywhere an id is accepted. Changing billing or settings needs the person to be an admin of the account: an organization admin, or the owner of a personal account.

## Connect over MCP

The MCP server is `https://www.sandchest.com/api/mcp` (Streamable HTTP). MCP clients sign in with OAuth on their own: the first time, a browser opens, the person signs in with GitHub and presses **Connect**.

```bash
# Claude Code
claude mcp add --transport http sandchest https://www.sandchest.com/api/mcp

# Codex
codex mcp add sandchest --url https://www.sandchest.com/api/mcp
```

For Cursor, VS Code and other clients, add a remote server with that URL:

```json
{
  "mcpServers": {
    "sandchest": { "url": "https://www.sandchest.com/api/mcp" }
  }
}
```

A client that can't do OAuth can send an [API key](#api-keys) instead, as the header `Authorization: Bearer <key>`.

## Connect over HTTP

Without MCP, use the device flow: one request starts it, the person approves in their browser, and polling returns an API key.

```bash
curl -s -X POST https://www.sandchest.com/api/v1/auth/device \
  -H 'content-type: application/json' -d '{"client_name":"My agent"}'
```

```json
{
  "device_code": "scd_…",
  "user_code": "BCDF-GHJK",
  "verification_uri_complete": "https://www.sandchest.com/device?code=BCDFGHJK",
  "expires_in": 900,
  "interval": 5
}
```

Give the person `verification_uri_complete` (and tell them the `user_code` it shows). Then ask for the key. With `wait=50` the request holds for up to 50 seconds until they approve, so you don't need a polling loop:

```bash
curl -s -X POST https://www.sandchest.com/api/oauth/token \
  -d grant_type=urn:ietf:params:oauth:grant-type:device_code \
  -d device_code=scd_… -d wait=50
```

It answers `authorization_pending` while they haven't approved yet (call it again), and then `{"access_token": "sck_…", "token_type": "Bearer"}`: an API key that doesn't expire. Without `wait` it answers at once, as the device flow standard says: poll every `interval` seconds, or it answers `slow_down`. The code expires after 15 minutes.

Then call the API with it:

```bash
curl -s https://www.sandchest.com/api/v1/me -H "Authorization: Bearer $SANDCHEST_API_KEY"
```

## API keys

API keys act as the person who made them, with exactly their access: the repositories GitHub says they can push to, and the accounts they administer. Make one for CI or a script in **Settings → Agents**, or with `create_api_key` from an agent connected with a key (MCP clients' OAuth tokens can't create keys). A key is shown once; Sandchest keeps only a hash of it. Revoke keys, and disconnect MCP clients, in **Settings → Agents** or with `revoke_api_key` (`"current"` revokes the key making the request).

If the person's GitHub sign-in expires or is revoked, calls answer `403 github_reauth_required`: they sign in once at [sandchest.com/sign-in](/sign-in) and the key works again.

## Tools and endpoints

Every tool is also an HTTP endpoint under `https://www.sandchest.com/api/v1`, with JSON in and out. Path parameters, query parameters and a JSON body are all accepted for a tool's arguments. `GET /api/v1` lists them, and [`/api/v1/openapi.json`](/api/v1/openapi.json) describes them in full.

| Tool | Endpoint | What it does |
| --- | --- | --- |
| `get_me` | `GET /me` | Who you act as, their accounts, and `next_steps` |
| `list_api_keys` | `GET /keys` | API keys and connected MCP clients |
| `create_api_key` | `POST /keys` | A new API key, shown once |
| `revoke_api_key` | `DELETE /keys/{id}` | Revoke a key or disconnect a client |
| `list_accounts` | `GET /accounts` | GitHub accounts Sandchest is installed on; `wait` while the person installs |
| `get_account` | `GET /accounts/{account}` | An account's settings, hacker and repositories |
| `update_account` | `PATCH /accounts/{account}` | Check threshold, emails, company details, first target |
| `update_hacker` | `PATCH /accounts/{account}/hacker` | The hacker's name, look and voice |
| `get_billing` | `GET /accounts/{account}/billing` | Plan, credits, auto top-up, free credits, prices; `wait` while the person pays |
| `quote_credits` | `POST /accounts/{account}/billing/quote` | Price a purchase without charging |
| `buy_credits` | `POST /accounts/{account}/billing/purchase` | Buy credits (or join the plan with them) |
| `claim_free_credits` | `POST /accounts/{account}/billing/claim` | Free credits, no card |
| `set_auto_top_up` | `PUT /accounts/{account}/billing/auto-top-up` | Buy credits automatically when they run low |
| `open_billing_portal` | `POST /accounts/{account}/billing/portal` | A Stripe link to change the card, see invoices or cancel |
| `set_invoice_details` | `PUT /accounts/{account}/billing/invoice-details` | Business name, address and tax ID on invoices |
| `list_repos` | `GET /repos` | Repositories, open findings, deep scan price |
| `get_repo` | `GET /repos/{repo}` | One repository, its recent scans and threat model |
| `start_deep_scan` | `POST /repos/{repo}/scans` | Deep scan a whole repository |
| `list_scans` | `GET /scans` | Scans, newest first |
| `get_scan` | `GET /scans/{id}` | A scan and its findings; `wait` up to 50 seconds |
| `get_scan_events` | `GET /scans/{id}/events` | The scan's live feed; `after` and `wait` |
| `list_findings` | `GET /findings` | Findings by status, severity and repository |
| `get_finding` | `GET /findings/{id}` | Attack path, proof of concept, fix guidance and prompt |
| `get_fix_prompt` | `GET /findings/{id}/fix-prompt` | The prompt that fixes it |
| `get_findings_prompt` | `GET /findings/prompt` | One prompt to fix many findings, or the list as Markdown or JSON |
| `update_finding` | `PATCH /findings/{id}` | Dismiss (with a reason), mark fixed, or reopen |
| `get_overview` | `GET /overview` | Reviews, scans, findings, fixes and credits over time |

`{repo}` is a repository's id or its full name (`/repos/acme/api`), and `{account}` an account's id or GitHub login.

Every step that waits on the person (approving the connection, installing the App, paying) takes `wait` (up to 50 seconds), so a single call returns as soon as it's done, without a polling loop.

## Errors

Errors come back as `{"error": {"code": "…", "message": "…"}}` with an HTTP status, and over MCP as a tool result with `isError`. The `message` is written to be passed on to the person. Codes to act on:

| Status | Code | What to do |
| --- | --- | --- |
| 401 | `unauthorized`, `invalid_token` | Connect again. The response says how. |
| 403 | `github_reauth_required` | The person signs in once at `sign_in_url`; the key then works again. |
| 402 | `no_plan`, `out_of_credits` | `get_billing`, then claim or buy credits. |
| 502 | `billing_unknown` | A purchase may or may not have gone through. Call `get_billing` before buying again. |
| 403 | `not_admin` | Only an admin of the account can do this. |
| 404 | `not_found`, `repo_not_found`, `account_not_found` | List them to find the right one. |
| 409 | `already_running` | Follow the running scan: its id is `scan_id`. |
| 409 | `over_max_usd` | The purchase cost more than your `max_usd`; nothing was charged. |
| 422 | `invalid_input` | `issues` lists each field that's wrong. |

## Paying safely

Card details never pass through an agent. The first payment for an account happens on Stripe's own page, which the person opens from `checkout_url`; Stripe saves the card for later. From then on `buy_credits` charges that card, so:

- always `quote_credits` first and tell the person what it will cost;
- pass `max_usd` to `buy_credits`, so nothing dearer than the quote is ever charged;
- if `buy_credits` fails with `billing_unknown`, check `get_billing` before buying again: the charge may have gone through;
- set `auto_top_up` with a `monthly_limit_usd` if they'd rather never run out.

See [Pricing & credits](/docs/pricing) for what each scan costs.
