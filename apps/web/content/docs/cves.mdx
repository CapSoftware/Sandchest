The CVEs page lists every known vulnerability that affects a version your repositories install, and shows where it is in your code: the package and version, the lockfile it comes from, and the files that import it, linked to the line on GitHub.

## Where the data comes from

- **What you install.** Sandchest reads each repository's manifests and lockfiles on its default branch: when a scan reads the repository, whenever a push to the default branch changes a manifest or lockfile, and on its own for every repository in use (a pull request reviewed, or a deep scan or fix check run, in the last 30 days). Any other repository is listed under **Not checked yet** with a **Check for CVEs** button. Reading them is free.
- **What is known.** Advisories come from [OSV](https://osv.dev), which collects GitHub's advisory database, the language advisory databases, CVEs with the commits they affect, and reports of malicious packages. Only package names, versions and commits are sent; never code.

| Language | Read from |
| --- | --- |
| JavaScript, TypeScript | npm, pnpm, Yarn and Bun lockfiles |
| Python | requirements files, Pipfile, Poetry, uv and PDM lockfiles, pyproject.toml |
| Go | go.mod |
| Java, Kotlin, Scala | Maven and Gradle builds, Gradle lockfiles and version catalogs, with versions set by parent POMs and BOMs and everything your artifacts pull in, read from Maven Central |
| Rust | Cargo.lock |
| PHP | composer.lock |
| Ruby | Gemfile.lock |
| C#, F#, Visual Basic | NuGet lockfiles, project files, central package management, packages.config |
| Dart, Flutter | pubspec.lock |
| Elixir, Erlang | mix.lock, rebar.lock |
| Julia | Manifest.toml |
| R | renv.lock |
| Swift | Package.resolved |
| Haskell | cabal.project.freeze, stack.yaml.lock |
| OCaml | opam lockfiles |
| C, C++ and anything vendored as a git submodule | the commit each submodule is pinned to |
| GitHub Actions | the actions your workflows use |

When OSV publishes or changes an advisory, Sandchest checks every repository that installs the package within a couple of minutes. Every repository is also checked in full once a day.

## In your code, installed or resolved

Each vulnerability is listed once, however many advisories describe it, and sorted by how exposed you are, then by severity.

- **In your code**: shipped code imports the affected version.
- **Installed**: the affected version is installed, but only as a dev dependency, pulled in by another package, imported only by tests, config or tooling, a git submodule, or in a language whose imports name modules rather than packages (Swift, Haskell, OCaml).
- **Resolved**: an upgrade removed the affected version, or the advisory no longer applies to it.

In a monorepo, each file counts for the version its own workspace resolves. When a lockfile holds three versions of a package, only the one your code actually loads is listed as in your code.

Severity is the advisory's own rating, or the one its CVSS score gives when it has none. A malicious package is always critical.

## Is this CVE in my code?

Search for a CVE id, an advisory id or a package name. If a CVE isn't listed, none of your repositories installs a version it affects. Opening `/dashboard/cves/CVE-2025-29927` directly answers the same question for one CVE.

## Fixing

A vulnerability's page shows the version that fixes each installed one, and **Copy upgrade prompt** gives your coding agent one prompt per repository: which packages to upgrade, from which lockfile, and how to confirm the old version is gone. Once the upgrade reaches the default branch, the vulnerability moves to resolved.

Agents can ask the same questions with `list_cves` and `get_cve`. See [Agents](/docs/agents).
