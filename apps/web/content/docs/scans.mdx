Sandchest runs four kinds of scan. All of them read your code in a temporary workspace that is deleted when the scan ends. None of them run your application, its tests or the proofs of concept they write.

| Scan | Runs when | What it does | Cost |
| --- | --- | --- | --- |
| Recon | A repository is added | Builds the repository's threat model | Free |
| PR review | A pull request is opened or updated | Reviews the change for vulnerabilities | What it uses, usually a few credits or less |
| Deep scan | You press **Deep scan** | Hunts across the whole repository | What it uses, usually well under 100 credits |
| Fix check | You push to the default branch | Re-checks open findings whose cited files the push changed | Free |

An account runs at most two scans at a time, and recon has two slots of its own, so a deep scan or a review never waits behind it. Others wait in a queue: each checks for a free slot every 10 seconds, says on its page that it is waiting, and gives up as failed after waiting two hours.

Repositories of a million lines of code or more aren't scanned, by any kind of scan. Get in touch if you need one scanned.

## Recon

Recon runs when Sandchest is installed on a repository, or a repository is added to the installation, once the account has a plan. It maps the repository the way an attacker would before trying anything:

- entry points: routes, handlers, command-line tools, jobs, queues and webhooks
- trust boundaries, and how authentication and authorization work
- sensitive data and where it is stored
- dangerous code: SQL, shell commands, file access, deserialization, outbound requests, templates and crypto
- protections the framework already gives you

The result is the repository's **threat model**: a structured summary, not a copy of your code. Every later scan of that repository starts from it. If a repository has no threat model yet, the next push to its default branch, pull request or deep scan builds one.

## PR reviews

A pull request is reviewed when it is opened, gets new commits, is reopened, or is marked ready for review. Each repository chooses how, under **Reviews and schedule** on its page in [Repos](/dashboard/repos). New repositories start from the account's choice under **Pull request reviews** in [Settings](/dashboard/settings), where an admin can also set every repository at once:

| Pull request reviews | What runs |
| --- | --- |
| Every push (the default) | Every push to an open pull request is reviewed |
| When asked | Only when someone with write access comments `/sandchest review` on the pull request, or presses **Review** on it in the repository's **Pull requests** list |
| Off | Nothing, and `/sandchest review` is ignored |

The repository's page lists its open pull requests with Sandchest's latest review of each. Press **Review** on one whose latest commit hasn't been reviewed: the button names the most it can cost, and a second press starts it. A commit whose review failed or ran out of credits can be reviewed again the same way, or with `/sandchest review`.

Even on Every push, some aren't reviewed automatically:

- drafts, until they are marked ready for review
- pull requests from forks of public repositories, and from outside contributors' forks of private ones (see [below](#pull-requests-from-forks))
- pull requests on an account with no plan, or out of credits: these get a neutral Check instead, once per pull request until the account can pay again

1. Sandchest posts a **Sandchest** Check straight away, showing "Scanning…".
2. It reviews the change in the context of the threat model. A finding has to touch the lines the pull request changed: issues that were already there are left for deep scans.
3. It completes the Check and writes its summary comment on the pull request. On private repositories, findings new to the pull request are also posted as review comments on the vulnerable lines.

PR reviews never wait behind deep scans: each kind of scan has its own place in the account's queue.

Each commit is reviewed once. A review is charged for what it uses; see [Pricing & credits](/docs/pricing#charged-for-what-it-uses).

### The Check

| Result | When |
| --- | --- |
| Failure | A finding is at or above your threshold (High, unless you change it) |
| Success | Nothing at or above the threshold |
| Neutral | Not reviewed: no plan, out of credits, or the review couldn't finish |

Set the threshold in [Settings](/dashboard/settings): Critical, High, Medium or Any. Low-confidence findings never fail a Check. A Check only blocks merging if you make it a required status check in GitHub's branch protection. A neutral Check never blocks.

### The summary comment

Sandchest keeps one comment on each pull request it reviews, and edits it after every review so it always describes the latest commit:

- **Nothing found:** "Sandchest reviewed `a1b2c3d`: nothing exploitable found in this change."
- **Findings:** how many, by severity, with a link to them in the dashboard. On private repositories it also lists each finding with its full write-up folded away; on public ones it says only how many (see below).
- **Still open from an earlier commit:** a finding an earlier review of the pull request reported stays on the comment, with the commit that found it, until it's fixed or dismissed. A later review that doesn't report it again says "nothing new found" instead of "nothing exploitable found". The Check describes the latest commit's review only.
- **A review that couldn't finish, or wasn't run** (out of credits): the comment says so, so an earlier result never stands in for the latest commit. A pull request that never had a summary just gets the neutral Check.

### Private repositories

Each finding new to the pull request is posted as a review comment on the last step of its attack path that is inside the diff, with its severity, what the attacker gets, who can exploit it, the attack path, a proof of concept, the fix, and a collapsed fix prompt for your coding agent. A finding already flagged on an earlier push isn't commented again: it stays in the summary comment, which holds every finding, including those whose lines are outside the diff. The Check lists every finding and what the review cost, for example "Reviewed · 2 credits".

### Public repositories

On a public repository, Checks and comments are visible to everyone. So Sandchest posts no review comments and no details: the Check and the summary comment say how many findings there are, by severity, with a link to the dashboard. Never what they are or where.

> Sandchest found 2 issues in `a1b2c3d` (1 high, 1 medium). This repository is public, so the details stay private: view them in the Sandchest dashboard →

The details are only in the dashboard, for people with push access.

### Pull requests from forks

- On **public** repositories, pull requests from forks are never reviewed automatically. A maintainer with write access comments `/sandchest review` on the pull request to start one.
- On **private** repositories, pull requests from forks are reviewed automatically when the author is an owner, member or collaborator. For anyone else, a maintainer comments `/sandchest review`.

The command has to be on a line of its own. Comments from people without write access, and from bots, are ignored.

Sandchest never opens GitHub issues.

## Deep scans

A deep scan hunts across the whole repository. It runs when someone presses **Deep scan** on the repository's page (open it from [Repos](/dashboard/repos)), or **Scan again** on a finished deep scan, or on the repository's schedule. Anyone who can push to the repository can start one. The button shows the most it can cost, and a second press confirms it.

- One deep scan runs at a time per repository. Once it finishes you can start another whenever you like: each one is charged for what it uses, never more than the button showed.
- A deep scan of a large repository typically takes 15 to 30 minutes, because every candidate is verified in a sandbox before it is reported.
- The scan's page shows a live feed of what Sandchest is doing, and findings appear as they survive verification.
- When it finishes, people with access get an email with what it found, unless an admin has turned emails off.

### Scheduled deep scans

Under **Reviews and schedule** on a repository's page, choose Daily, Weekly or Monthly to keep it scanned without anyone pressing anything. Each scheduled scan costs what **Scan again** would.

- The first one is due an interval after the last deep scan, or within ten minutes if there was none or it's overdue. The page shows when the next one is.
- A scheduled scan is skipped when the default branch hasn't changed since the last deep scan, so the same code is never paid for twice.
- It's skipped if a deep scan is already running, or the account is out of credits. The next one is still due on time.
- Anyone who can push to the repository can change the schedule.

## Fix checks

When you push to the default branch, Sandchest checks the repository's open findings whose cited files that push changed, and its vulnerable-dependency findings when the push changes a lockfile or manifest. Other open findings aren't touched. Each one is checked again on the new code:

- Each step of the attack path is found again by its code, so findings follow code that moved. If the fix rewrote the vulnerable line itself, the finding is checked from the rest of its path.
- The reviewer sees what the push changed and judges the code as it is after it. The finding is marked **fixed** only when it can point to code that now blocks the attack. Moving, renaming or reformatting the code, or fixing one path while another still reaches it, leaves it open. A fixed finding's code excerpts are deleted.
- A vulnerable dependency is marked **fixed** when the package is gone or every installed version is clear of the advisories the finding names. It stays open while the reported version is still installed.
- If none of the cited code can be found any more, the finding stays open and is marked **Code moved**. The mark clears when a later scan finds the same finding again. Sandchest never closes a finding just because it lost track of the code.

Fix checks are free, and run even when the account has no credits left.

## How Sandchest finds vulnerabilities

PR reviews and deep scans run the same pipeline:

1. **Signal sweep.** A fast, deterministic pass finds leaked secrets, vulnerable dependencies that your code actually calls, and dangerous code reachable from an entry point. These are leads, not findings.
2. **Hunt.** Several attacker agents work in parallel from the threat model and the leads. They think like outsiders, free-tier users, fraudsters and insiders, and trace untrusted input from entry points to dangerous code, chaining weaknesses together.
3. **Evidence gate.** A candidate is kept only if it names the exact entry point, cites every step from input to impact by file and line (each citation is checked against your code), states who can exploit it, and includes a proof of concept and its impact in plain English.
4. **Skeptic.** A separate reviewer reads the cited code and tries to disprove each finding: middleware, validation, framework defaults, unreachable code. It can only drop a finding by citing the code that disproves it. Each survivor gets a confidence: high, medium or low.
5. **Write-up.** The finding is written up with a title, severity, fix guidance and a fix prompt. Code excerpts are read from your repository, never written by the model.

Repository content is treated as untrusted data. The model is told to ignore any text in code, comments or pull requests that tries to instruct it, and to report it as a prompt injection finding. That makes manipulation harder, but it isn't a guarantee.
